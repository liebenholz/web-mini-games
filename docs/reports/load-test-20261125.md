## 2. 해석

- **400방(접속 약 1,000)까지는 여유가 크다.** CPU, 메시지, 메모리가 방 수에 정비례하고 이벤트 루프 p99는 3ms 아래다.
- **800방(접속 약 2,000)부터 지연이 비례 이상으로 늘었다.**
  - p99가 400방의 약 2~5배다 (중앙값 5ms, 최고 13ms).
  - 0.1~0.4초짜리 멈춤이 몇 분마다 생긴다. 이때 착수나 선언이 한 박자 늦게 보일 수 있다.
  - 그래도 입장 실패나 판 오류는 없었다.
- **메모리는 제약이 아니다.** 800방에서 305MB로 한도 8GB의 4%다.
- **병목은 Node 프로세스 하나의 CPU(코어 1개)다.** VM은 2코어인데 게임 서버는 한 코어만 쓴다. 800방에서 이벤트 루프 사용률이 51%였으니, 같은 비율이면 약 1,500방에서 코어 1개가 다 찬다 (측정하지 않은 추정).
- **DB, Redis, Caddy는 한계와 거리가 멀다.**

## 3. 병목과 개선 항목

1. **순간 멈춤(최대 지연)이 커진다.** 방이 많을수록 판 종료가 몰리는 순간이 잦아진다. 이때 기록 저장, 방 정리, 새 방 만들기가 한꺼번에 일어난다. GC도 원인일 수 있다. 400방 이상을 받을 일이 생기면 CPU 프로필로 원인을 나눠 본다.
2. **2번째 코어를 쓰지 않는다.** Colyseus는 이미 Redis presence와 driver를 쓰고 있어, 같은 VM에서 서버 프로세스를 2개로 늘려도 방을 나눠 맡을 수 있다. 필요해지면 수용량을 약 2배로 늘리는 가장 쉬운 방법이다. 지금은 필요 없다.
3. **게임별 프로세스 분리는 필요 없다** (Phase 2 M6 질문). 혼합 부하에서 어느 게임도 따로 튀지 않았다. 확인하려면 게임별 측정이 필요하다 (4장).
4. **API 주소가 외부 무료 DNS(sslip.io)에 의존한다.** 측정 중 생성기 쪽에서 DNS 조회 실패가 1건 있었다. 실제 사용자도 겪을 수 있으므로, 정식 도메인과 Cloudflare DNS로 옮기는 일(🙋 Phase 1 M5)의 우선순위를 올린다.

## 4. 하지 않은 것

- **게임별 단독 측정** (`--mix <게임>:1`): Phase 2 M6 완료 기준의 "게임별 최대 동시 방 수"는 아직 측정하지 않았다. 혼합 결과로 보면 400방까지는 어느 게임이든 여유가 있다. 다음 측정 때 게임마다 200·400방을 돈다.
- **1,000방 이상:** 생성기 한 대로도 갈 수 있지만, 순간 멈춤이 이미 커지는 구간이라 멈췄다.
- **장시간(수 시간) 측정:** 메모리가 새지 않는지는 단계별 5분 안에서만 봤다. GC 뒤 메모리가 다시 내려오는 것은 확인했다.
