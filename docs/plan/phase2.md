# Phase 2 작업 계획: 게임 선택 화면 + 두 번째·세 번째 게임

## 목표

WMG(Web Multiplayer Ground)를 "게임 하나짜리 사이트"에서 "여러 게임을 고르는 플랫폼"으로 바꾼다.

1. 첫 화면은 **게임만 고르는 메인 페이지**다. 닉네임은 묻지 않는다.
2. 닉네임은 **게임마다 따로** 정하고 저장한다. 게임 로비에 들어가서 처음 정한다.
3. Phase 1의 공통 프레임워크(방, 턴, 재접속, 봇, 배포) 위에 **오목**과 **원카드**를 추가한다.

이 과정에서 "새 게임을 붙이는 방법"을 정리해, Phase 3부터는 게임 추가가 명세와 게임 코드만으로 끝나게 한다.

## 진행 방식

Phase 1과 같다.

- 마일스톤은 순서대로 진행하고, 완료 기준과 `pnpm -r test`, `pnpm lint`, `pnpm typecheck`, E2E가 통과해야 다음으로 넘어간다.
- 화면을 새로 만들거나 크게 바꾸면 **구현 전에 시안을 보여 주고 확인을 받는다.**
- 게임 규칙은 **명세(`docs/specs/<게임>.md`)를 먼저 쓰고 승인받은 뒤** 구현한다. 아래 "결정 필요" 항목은 명세를 쓸 때 사람이 정한다.
- 🙋 표시는 사람이 직접 하는 작업이다.

## 게임 선정

| 게임                  | 인원 | 넣는 이유                                                                                           | 새로 검증하는 것                                       |
| --------------------- | ---- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **오목**              | 2    | 규칙이 단순하고 모두 안다. 두 번째 게임을 붙이는 구조를 가장 적은 게임 코드로 검증한다               | 공개 정보 보드 게임, 1:1 방, 승패 판정, 보드 봇        |
| **원카드**            | 2~6  | 라이어 다이스처럼 숨겨진 정보(내 패)와 여러 명이 하는 게임이라 공유하기 좋다                         | 카드 덱과 패 관리, 특수 카드 규칙, 턴 방향 바꾸기      |
| 숫자야구 (선택)       | 2    | 시간이 남으면 넣는다. 가볍고 규칙을 다 안다                                                          | 비밀 숫자, 동시 진행 턴                                |

후보에 있던 빙고, 리버시, 사목, 끝말잇기, 그림 맞히기는 Phase 3 이후로 둔다. 다른 회사 게임의 이름과 아트는 쓰지 않는다 (CLAUDE.md).

서버 부담: 셋 다 턴제이고 방 하나가 수십 KB 수준이라 2 OCPU / 12GB 한 대에서 같은 프로세스에 방 종류만 늘려 돌린다. 게임별로 프로세스를 나눌지는 M6 부하 테스트 결과로 정한다.

## M0. 여러 게임 구조 결정 (ADR 0002)

코드를 쓰기 전에 아래를 정해 `docs/adr/0002-multi-game-platform.md`에 남긴다.

- **주소 체계**: `/` 메인(게임 선택), `/<게임>` 게임 로비, `/<게임>/r/<방 코드>` 초대 링크.
  - 기존 `/r/<코드>`와 `/liars-dice`는 계속 동작하게 거짓말쟁이 주사위로 연결한다 (이미 공유된 링크 보호).
- **게임 목록(registry)**: 게임마다 id, 이름, 인원, 플레이 시간, 한 줄 소개, **카테고리**(주사위/카드/보드), 상태(플레이 가능/준비 중)를 한곳에 정의한다. 메인 페이지, 로비, 규칙 시트, 링크 미리보기가 이 목록을 읽는다.
  - 카테고리는 지금부터 넣어 두고, 화면에서는 Phase 3에서 쓴다 (아래 "Phase 3에서 할 것").
- **게임별 닉네임**: `wmg.<게임>.nickname`으로 따로 저장한다. 게스트 ID는 사람을 구분하는 값이라 모든 게임이 하나를 같이 쓴다.
  - 기존 `wmg.nickname`은 거짓말쟁이 주사위 닉네임으로 한 번 옮긴다.
- **코드 위치**: 게임 코드는 게임 폴더에, 공통 코드는 프레임워크 폴더에 둔다.
  - `packages/rules/src/games/<게임>/`, `packages/server/src/games/<게임>/` (이미 이 형태), `packages/client/src/games/<게임>/`
  - 공통: 방 코드, 닉네임, 재접속, 턴 타이머, 봇 지연, 결과 화면, 규칙 시트 틀
- **방 종류**: 서버는 게임마다 Colyseus 방 종류를 하나씩 등록한다 (`liars_dice`, `omok`, `one_card`). 방 코드는 모든 게임이 같은 공간을 쓰고, 초대 링크의 게임과 실제 방의 게임이 다르면 `ROOM_NOT_FOUND`로 거부한다.
- **DB**: `games` 테이블에 `game_type` 컬럼을 추가한다. 게임별 라운드·수 기록 테이블은 게임마다 정한다.

**완료 기준**

- [ ] ADR 0002 승인
- [ ] 위 결정과 다르게 이미 만들어진 부분(예: `GAME_ID` 상수 하나)의 이전 계획이 ADR에 있다

## M1. 메인 페이지와 게임별 로비

- **메인 페이지** (`/`): 게임 카드 목록만 보여 준다. 닉네임, 방 코드 입력은 없다.
  - 카드: 게임 이름, 한 줄 소개, 인원, 플레이 시간, "규칙 보기", 준비 중 게임은 비활성 표시
  - 방 코드를 받은 사람은 초대 링크로 바로 들어가므로 메인에는 코드 입력을 두지 않는다
  - 🎨 구현 전에 시안 확인
- **게임 로비** (`/<게임>`): 지금의 거짓말쟁이 주사위 로비를 공통 틀로 바꾼다. 상단에 "← 게임 목록"을 둔다. 닉네임은 이 화면에서 정하고 게임별로 저장한다.
- **규칙 시트 일반화**: 게임마다 규칙 내용만 넘기면 같은 시트로 보여 준다. 메인 카드의 "규칙 보기"와 로비 버튼이 같은 시트를 연다.
- **링크 미리보기**: 메인과 게임별로 Open Graph 제목, 설명, 이미지를 넣는다. 카카오톡과 디스코드에서 초대 링크가 카드로 보인다.
- **기존 링크 호환**: `/r/<코드>`, `/liars-dice` 그대로 동작

**완료 기준**

- [ ] `/`에서 게임을 골라 로비 → 방 만들기 → 한 판 완주 (E2E)
- [ ] 게임 A에서 정한 닉네임이 게임 B 로비에 나오지 않는다 (E2E)
- [ ] 기존 `/r/<코드>` 초대 링크로 거짓말쟁이 주사위 대기실에 들어간다 (E2E)
- [ ] 360px에서 카드와 버튼이 잘리지 않는다
- [ ] 카카오톡 링크 미리보기에 제목과 이미지가 나온다 🙋 (직접 확인)

## M2. 오목

- 명세 `docs/specs/omok.md` (규칙 ID O-xx). **결정 필요:**
  - 판 크기 (기본 15×15)
  - 금수 규칙: 없음(자유 오목) / 흑에게 3-3 금지 / 렌주 규칙 (3-3, 4-4, 장목 금지)
  - 장목(6개 이상)을 승리로 볼지
  - 선(흑) 정하기: 무작위, 리매치 때 바꾸기
  - 턴 시간과 시간 초과 처리 (자동 착수 / 패배)
  - 무르기 없음 (기본)
- 룰 엔진: 착수 검증, 5목 판정, (선택한) 금수 판정. 순수 함수와 단위 테스트
- 서버 방: 2인 방, 관전, 재접속, 시간 초과, 봇(빈자리 채우기)
- 봇: 연결 수 평가로 막고 두는 수준. 강할 필요는 없다
- 클라이언트: 15×15 판(360px에서 칸이 손가락으로 눌리는 크기), 마지막 수 표시, 착수 전 미리 보기
- DB: 착수 순서 저장, 리플레이 검증

**완료 기준**

- [ ] 명세의 모든 규칙에 단위 테스트 (규칙 ID 포함)
- [ ] 사람 1명 + 봇으로 한 판 완주 (E2E)
- [ ] 두 브라우저로 초대 링크 대전, 재접속 복원
- [ ] 360px에서 판 전체가 보이고 오착수 없이 둘 수 있다

## M3. 원카드

- 명세 `docs/specs/one-card.md` (규칙 ID C-xx). 지역마다 규칙이 달라서 **결정할 것이 가장 많다:**
  - 덱 구성 (52장 + 조커 2장?), 시작 패 수 (예: 7장)
  - 특수 카드: 공격(2, A, 조커)과 공격 누적·방어, 모양 바꾸기(7), 건너뛰기(J), 방향 바꾸기(Q), 한 번 더(K)
  - "원카드" 외치기와 못 외쳤을 때 벌칙 (넣을지, 시간 제한)
  - 패가 일정 수를 넘으면 탈락(파산)할지
  - 승리 조건: 먼저 다 낸 1명 / 끝까지 순위 매기기
  - 덱이 떨어지면 버린 카드 섞기
- 룰 엔진: 낼 수 있는 카드 판정, 공격 누적, 방향과 다음 차례 계산
- 서버 방: 2~6인, 패는 본인에게만 (S-01과 같은 원칙), 시간 초과 자동 행동, 봇
- 클라이언트: 내 패 부채꼴, 낼 수 있는 카드 강조, 상대 패 수, 공격 누적 표시

**완료 기준**

- [ ] 명세의 모든 규칙에 단위 테스트
- [ ] 다른 사람의 패가 어떤 메시지에도 들어가지 않는다 (라이어 다이스 TC-08과 같은 검사)
- [ ] 사람 1명 + 봇 3명으로 한 판 완주 (E2E)
- [ ] 360px에서 패 7장 이상이 겹쳐도 고를 수 있다

## M4. 숫자야구 (선택)

M3까지 끝나고 여유가 있을 때만 한다. 명세 → 룰 → 방 → 화면 순서는 같다.

## M5. 배포와 운영

- `v0.2.0` 태그로 서버와 클라이언트 배포
- 메인 페이지 통계: Cloudflare Web Analytics(쿠키 없음)로 게임별 진입 수를 본다 🙋 (대시보드에서 켜기)
- 게임별 판 수를 DB에서 볼 수 있는 간단한 쿼리를 운영 문서에 적는다

**완료 기준**

- [ ] 운영 주소에서 세 경로(메인 → 오목, 메인 → 원카드, 기존 초대 링크) 모두 동작
- [ ] 배포 중 진행 중인 판이 끊기지 않는다

## M6. 부하 테스트

Phase 1 M6을 여러 게임으로 넓힌다. 게임을 섞어 동시 방 수를 늘리며 메모리, CPU, 지연을 잰다.

**완료 기준**

- [ ] 서버 컨테이너 메모리 8GB 이내(VM 2 OCPU / 12GB)에서 게임별·혼합 최대 동시 방 수 문서화
- [ ] 게임별 프로세스 분리가 필요한지 결론

## Phase 3에서 할 것

- **카테고리 계층**: 게임이 6~8개를 넘으면 메인을 "주사위 / 카드 / 보드" 같은 카테고리 → 게임 순서로 바꾼다. M0의 게임 목록에 카테고리를 미리 넣어 두므로 화면만 바꾸면 된다.
- 다른 후보 게임 (빙고, 리버시, 사목, 끝말잇기, 그림 맞히기)
- 게임 중 화면에서 규칙 다시 보기

## 이번 단계에서 하지 않는 것

- 로그인, 친구 목록, 채팅
- 게임 간 통합 닉네임 (게임별로 정한다)
- 베팅, 재화, 결제, 광고
