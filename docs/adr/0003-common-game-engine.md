# ADR 0003: 게임 공통 엔진 (게임을 10개, 30개로 늘리기 전에)

- 상태: 승인 (2026-11-26)
- 날짜: 2026-11-26
- 관련: `docs/plan/phase2.md` "Phase 3에서 할 것", ADR 0002

## 배경

v0.6.0에서 게임을 10개까지, 장기적으로 20~30개까지 늘린다. ADR 0002의 목표는 "Phase 3부터 게임 추가가 명세와 게임 코드만으로 끝난다"였지만, 지금은 게임마다 공통 코드를 복사하고 있다 (2026-11-26 측정).

| 코드                             | 게임마다      | 서로 다른 부분                                                                                                                                                  |
| -------------------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 서버 방 (`*Room.ts`)             | 230~260줄 × 4 | 이름을 맞추면 약 26줄 (90% 같음)                                                                                                                                |
| 서버 진행 (`*Match.ts`)          | 670~900줄 × 4 | 메서드 약 25개가 같은 일을 한다: 입장·퇴장·재접속, 준비, 방장, 추방, 봇 추가·삭제, 시작 조건, 이탈 대체(S-10, G-22), 리매치, 모두 나감(E-10), 타이머, 목록 공개 |
| 클라이언트 세션 (`session.ts`)   | 220~270줄 × 4 | 약 70줄 (70% 같음)                                                                                                                                              |
| 클라이언트 대기실 (`waiting.ts`) | 200~215줄 × 3 | 약 66줄 (옵션 칸만 다름)                                                                                                                                        |

공통 기능 하나를 넣을 때 네 군데를 똑같이 고쳐야 한다 (예: 이탈 기록 ST-08, 접속 실패 보고 CE-01). 30개면 30군데이고, 한 곳만 빠져도 버그가 된다. 또 메인 번들이 모든 게임 화면 코드를 처음부터 싣는다 (90KB gzip, 게임 수에 비례해 커진다).

## 결정

### 1. 서버: 공통 방과 공통 진행 + 게임 모듈

`packages/server/src/framework/game/`에 둔다.

- **`GameRoom`** (Colyseus Room 공통): 방 코드 발급과 presence, 빈도 제한(E-14), 클라이언트 ↔ playerId 연결, 재접속 대기(S-08), 추방 종료 코드, 목록 공개, 활성 방 등록, 모두 나감 기록(ST-09), dispose 정리. 게임은 방 종류 이름과 게임 모듈만 넘긴다.
- **`LobbyMatch`** (대기실과 좌석 공통): 구성원(사람·봇·관전자), 입장 순서, 방장 위임(E-09), 준비, 옵션 변경(방장만), 봇 추가·삭제, 추방(E-15), 시작 조건(최소 인원, 전원 준비, 빈자리 봇 채우기), 게임 중 퇴장·끊김·복귀와 봇 대체, 이탈 기록(ST-08), 리매치, 모두 나감(E-10), 턴 타이머와 봇 지연(원칙 7), 판 기록 저장 호출.
- **게임 모듈** (`GameModule`): 게임마다 남는 부분만 구현한다.
  - 옵션: 기본값, 검증(`parse…Options`), 인원 범위
  - 시작: 좌석이 정해지면 게임 상태를 만든다
  - 행동: 게임 메시지 처리 (`place`, `bid`, `play` …)와 검증
  - 봇: 차례가 오면 할 행동, 시간 초과 때 자동 행동
  - 공개 상태 동기화(schema)와 본인에게만 보내는 정보 (S-01 원칙 그대로)
  - 끝: 결과와 판 요약 (`GameSummaryRecord`)
- 공유 상태(schema)는 공통 필드(단계, 방 코드, 방장, 구성원 공통 필드, 차례, 마감 시각)와 게임 필드로 나눈다. 숨겨진 정보는 계속 schema에 넣지 않는다 (원칙 4).

### 2. 프로토콜: 공통 메시지는 한 곳에

대기실 메시지(`set_ready`, `start_game`, `set_options`, `add_bot`, `remove_bot`, `kick_player`, `rematch`, `leave_room`)와 공통 서버 메시지(`welcome`, `turn_start`, `player_replaced`, `error`), 공통 에러 코드를 `packages/rules/src/lobby/`에 한 번만 정의한다. 게임 프로토콜은 그 위에 게임 메시지만 더한다. **메시지 이름과 모양은 바꾸지 않는다** (배포 중인 클라이언트와 호환).

### 3. 클라이언트: 공통 세션, 공통 대기실, 게임별 지연 로딩

- **`RoomSession`**: 만들기·입장·빠른 매칭, 재접속, 오류 보고(CE-01), 닫힘 이유, 시계 보정을 한 번만 구현한다. 게임은 상태를 화면용 값으로 바꾸는 함수와 게임 메시지 처리만 넘긴다.
- **대기실 틀**: 좌석 목록, 준비, 방 코드, 봇, 추방, 시작 버튼은 공통이고, 게임은 옵션 칸만 그린다.
- **지연 로딩**: 게임 목록(registry)에는 정보만 두고, 게임 화면 코드는 `load: () => import('./<게임>/index.js')`로 그 게임에 들어갈 때 불러온다. 메인 번들은 게임 수와 상관없이 일정하게 둔다.

### 4. 게임 목록 정보 확장 (검색·필터 준비)

게임마다 인원(최소~최대), 플레이 시간, 카테고리, 1:1 여부, 숨긴 정보 여부, 검색용 별칭을 registry에 둔다. 메인의 검색·필터는 이 값을 읽는다 (별도 명세).

### 5. 새 게임 추가 가이드

`docs/guides/new-game.md`에 순서를 적는다: 명세 → 룰(`packages/rules/src/games/<게임>`) → 게임 모듈 → 화면 → 테스트(룰 단위, 모듈 통합, E2E 한 판 완주). 이 문서만 보고 게임을 붙일 수 있어야 한다.

## 이전 순서

**모든 단계는 동작을 바꾸지 않는다.** 기존 단위·통합·E2E 테스트가 그대로 통과해야 다음 단계로 간다. 단계마다 PR 하나다.

| 단계 | 내용                                                                                      | 확인                                            |
| ---- | ----------------------------------------------------------------------------------------- | ----------------------------------------------- |
| P1   | 서버 `GameRoom`·`LobbyMatch`·`GameModule`을 만들고 **오목**을 옮긴다 (가장 작은 2인 게임) | 오목 테스트 전부, E2E                           |
| P2   | **숫자야구, 원카드**를 옮긴다                                                             | 각 게임 테스트, E2E                             |
| P3   | **거짓말쟁이 주사위**를 옮긴다 (가장 오래됐고 `seq` 봉투, 라운드 구조가 있다)             | 주사위 테스트(TC-01~14 포함), soak 1,000판, E2E |
| P4   | 클라이언트 공통 세션·대기실, 게임별 지연 로딩, 공통 프로토콜 정리                         | 클라이언트 테스트, E2E, 메인 번들 크기 비교     |
| P5   | 새 게임 가이드를 쓰고, 그 가이드대로 **리버시**를 붙인다 (새 구조의 검증)                 | 가이드만으로 붙였는지                           |

각 단계는 서버 배포를 따로 하지 않아도 된다. P3까지 끝나면 한 번 배포해도 되고, 단계마다 배포해도 된다 (동작이 같으므로).

## 고려한 대안

- **지금처럼 복사:** 게임 하나를 가장 빨리 붙일 수 있다. 하지만 공통 수정이 게임 수만큼 늘고 빠뜨리기 쉽다. 10개를 넘으면 유지가 어렵다.
- **외부 게임 프레임워크 도입:** 새 의존성이 생긴다 (CLAUDE.md). 지금의 서버 권한형, 숨긴 정보 전송 방식, Colyseus 방 구조와 맞추는 비용이 크다.
- **게임마다 프로세스 분리:** 부하 테스트 결과 필요 없다 (`docs/reports/load-test-20261125.md`). 코드 중복 문제도 풀지 못한다.

## 영향

- 사용자에게 보이는 변화는 없다. 주소, 메시지, 저장 형식이 같다.
- 리팩터 범위가 커서 단계별 PR로 나누고, 단계마다 E2E를 돌린다. 단계 사이에도 main은 항상 배포 가능한 상태다.
- P1~P4 동안 새 게임 추가는 멈춘다. 대신 P5부터는 게임 하나에 드는 코드가 룰, 모듈, 화면으로 줄어든다.
- 공통 엔진에 넣기 어려운 게임별 흐름(주사위의 라운드·공개 연출, 원카드의 원카드 외치기 창, 숫자야구의 비밀 숫자 단계)은 게임 모듈의 단계 훅으로 둔다. 무리하게 일반화하지 않는다.
