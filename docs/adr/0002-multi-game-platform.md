# ADR 0002: 여러 게임을 담는 플랫폼 구조

- 상태: 제안 (리뷰 필요)
- 날짜: 2026-11-24
- 관련: `docs/plan/phase2.md` M0, M1

Phase 1은 거짓말쟁이 주사위 하나를 전제로 만들었다 (첫 화면이 곧 그 게임의 로비, `GAME_ID` 상수 하나, 닉네임 하나). Phase 2부터 게임을 고르는 메인 화면을 두고 게임을 하나씩 늘리기 위해 아래처럼 정한다.

## 결정

### 1. 주소

| 주소                  | 화면                                       |
| --------------------- | ------------------------------------------ |
| `/`                   | 메인: 게임 선택만 (닉네임, 코드 입력 없음) |
| `/<게임>`             | 게임 로비: 닉네임, 방 만들기, 코드 입장    |
| `/<게임>/r/<방 코드>` | 초대 링크: 그 게임의 대기실로 바로         |

- 게임 주소 이름은 영문 소문자와 하이픈 (`liars-dice`, `omok`, `one-card`).
- **기존 주소 호환**: `/r/<코드>`는 거짓말쟁이 주사위 초대 링크로 처리한다 (이미 공유된 링크). `/liars-dice`는 그대로 로비다. 새로 만드는 초대 링크는 `/<게임>/r/<코드>` 형식이다.
- 준비 중인 게임의 주소로 들어오면 메인으로 보내고 "준비 중인 게임입니다"를 알린다.

### 2. 게임 목록 (registry)

`packages/client/src/games/registry.ts` 한곳에 게임마다 아래 값을 둔다. 메인 카드, 로비 머리말, 규칙 시트, 링크 미리보기가 모두 이 값을 읽는다.

| 필드       | 예 (거짓말쟁이 주사위)                    |
| ---------- | ----------------------------------------- |
| `id`       | `liars-dice` (주소)                       |
| `roomType` | `liars_dice` (서버 방 종류, 기존 값 유지) |
| `name`     | 거짓말쟁이 주사위                         |
| `tagline`  | 내 주사위를 단서로 거짓말은 잡아내요      |
| `players`  | 2~6명                                     |
| `minutes`  | 5~10분                                    |
| `category` | `dice` / `card` / `board`                 |
| `status`   | `available` / `coming-soon`               |
| `rules`    | 규칙 시트 내용 (게임 모듈에서 불러옴)     |

- **코드가 없는 게임은 `coming-soon`**이다. 메인에 카드는 보이지만 누를 수 없고 규칙 보기도 없다. 오목과 원카드는 구현되는 마일스톤에서 `available`로 바꾼다.
- `category`는 Phase 3의 카테고리 → 게임 계층 화면에서 쓴다. 지금은 화면에 쓰지 않는다.

### 3. 닉네임과 게스트 ID

- 닉네임은 게임마다 따로 저장한다: `localStorage['wmg.<게임 id>.nickname']`.
- 기존 `wmg.nickname` 값은 처음 한 번 `wmg.liars-dice.nickname`으로 옮기고 지운다.
- 게스트 ID(`wmg.guestId`)는 사람(브라우저)을 구분하는 값이라 모든 게임이 하나를 같이 쓴다. 다른 사람에게는 여전히 공개하지 않는다.

### 4. 서버 방과 방 코드

- 게임마다 Colyseus 방 종류를 하나씩 등록한다 (`liars_dice`, 이후 `omok`, `one_card`). 한 프로세스에서 같이 돈다.
- **방 코드는 모든 게임이 같은 공간을 쓴다.** Colyseus의 방 ID가 프로세스 전체에서 하나여야 하기 때문이다. Redis 키를 `wmg:liars_dice:codes`에서 `wmg:room-codes`로 옮긴다.
- 초대 링크의 게임과 실제 방의 게임이 다르면 클라이언트는 `ROOM_NOT_FOUND`로 처리한다 (다른 게임의 방에 잘못 들어가지 않게).
- `GAME_ID` 상수는 게임별 `ROOM_TYPE`으로 바꾸고, 클라이언트는 registry의 `roomType`을 쓴다.

### 5. 코드 위치

| 패키지   | 게임 코드                          | 공통 코드                                       |
| -------- | ---------------------------------- | ----------------------------------------------- |
| `rules`  | `src/games/<게임>/`                | 방 코드, 닉네임, 방 옵션 기본 검증, 프로토콜 틀 |
| `server` | `src/games/<게임>/` (이미 이 형태) | 프레임워크(스케줄러, 난수, 요청 제한), 저장     |
| `client` | `src/games/<게임>/`                | 메인, 로비 틀, 대기실 틀, 규칙 시트, 연결, 결과 |

거짓말쟁이 주사위 코드를 이 구조로 옮기는 일은 동작을 바꾸지 않는 리팩터링으로 따로 PR을 만든다.

### 6. 기록 (DB)

- `games` 테이블에 `game_type text NOT NULL DEFAULT 'liars_dice'` 컬럼을 추가하는 마이그레이션을 만든다. 기존 기록은 거짓말쟁이 주사위로 채워진다.
- 라운드와 수 기록은 게임마다 구조가 달라서 게임별 테이블로 둔다 (`rounds`, `bids`는 거짓말쟁이 주사위 전용으로 남는다).

## 고려한 대안

- **초대 링크를 `/r/<코드>` 하나로 두고 방 종류를 서버에 물어보기**: 링크가 짧지만, 들어가기 전에 그 게임의 닉네임을 물어야 해서 한 번 더 요청이 필요하다. 링크에 게임이 보이면 미리보기 문구도 게임별로 만들 수 있어서 게임을 주소에 넣는다.
- **닉네임 하나를 모든 게임에서 공유**: 입력이 한 번이면 되지만, 요청 사항대로 게임마다 따로 쓴다.
- **게임마다 서버 프로세스 분리**: 격리는 좋지만 지금 부하에서는 운영만 복잡해진다. M6 부하 테스트 결과로 다시 본다.

## 영향

- 기존 초대 링크, 저장된 닉네임, DB 기록은 그대로 쓸 수 있다.
- 새 게임 추가 = 명세 + `rules`/`server`/`client`의 게임 폴더 + registry 한 줄.
